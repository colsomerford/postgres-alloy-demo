# Postgres DB Observability with Grafana and Alloy

### Postgres requirements

Due to the nature by which the database_observabiltiy.postgres component relies on gathering information and statistics that is generated by Postgres, there are some strict setup processes required to be run on the Postgres server / databases you wish to monitor.

These are called out explicitly in the instructions here <https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-applications/database-observability/set-up/postgres/> it's worth noting that following the instructions precisely the first time setting it up is a necessity and will likely need to be stressed to the DBA's implementing it. This includes (at least for the first test run) setting the same username as documented for the monitoring user, simply due to the fact that when using the Fleet Management to set things up, along with "excluding" queries that the monitoring user uses to connect to the database, the username used is required to be in sync. While changing is obviously possible - it then needs making sure other entries reflect this.

Key things to call out for the setup are:

1) System Level settings in the postgres.conf file are required, as these are needed to persist. These **MUST** include
    - shared_preload_libraries = 'pg_stat_statements'
    - compute_query_id = on
    - pg_stat_statements.track = all
    - track_activity_query_size = 4096

1) db-o11y (the default monitoring user) **MUST** have the following roles applied to them
    - GRANT pg_monitor TO "db-o11y";
    - GRANT pg_read_all_stats TO "db-o11y";
    - GRANT pg_read_all_data TO "db-o11y";

This ensures the statistics AND the ability to run the execution plans are granted.

2) If you wish to process logs - which is requried for some of the Error Rate numbers, you **MUST** have the following to setup the logs in a particular format. Note - because this physically changes the layout of the log entries - if the postgres logs are being monitored currently by any other means - **CHECK THIS WILL NOT BREAK THAT FUNCTIONALIY**
    - logging_collector = on
    - log_directory = '/var/log/postgresql'
    - log_filename = 'postgresql-%Y-%m-%d.log'
    - log_line_prefix = '%m:%r:%u@%d:[%p]:%l:%e:%s:%v:%x:%c:%q%a:'
    - log_destination = 'stderr'

    If required the log can be written elsewhere, however you must match the loki source definition in Alloy to read the relevant file. Also note while there is the directive of "log_destination='std_err'" in this case it really only determines the format of the messaging

2) CREATE EXTENSION IF NOT EXISTS pg_stat_statements; MUST be run in EVERY database that you are going to configure database_observability.postgres to conect to.

3) ALTER ROLE "db-o11y" SET pg_stat_statements.track = 'none'; This is so that the statements for the monitoring user don't take up memory and resources of the tracking system as it is a global pool
